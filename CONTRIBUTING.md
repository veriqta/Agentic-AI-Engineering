# Contributing

Welcome! Contributions that improve accuracy, accessibility, test coverage, documentation and reproducibility are encouraged.

1. Open an issue describing the change, unless it is a small typo fix.
2. Create a branch and make focused changes.
3. Run relevant tests and document tested Python and dependency versions.
4. Submit a pull request with a clear description and actual evidence.

Do not submit secrets, fabricated execution outputs, copyrighted assets without permission or claims of production readiness without supporting tests. Be respectful and constructive.

## Public documentation standard

Write for a worldwide learning community. Address readers as learners or contributors, use self-contained explanations and state prerequisites explicitly. Keep personal tutoring notes, private conversations, individual progress records and account authorization details out of repository content. Use VERIQTA Academy as a clearly described project example. Publish only authentic, reviewed and appropriately redacted execution evidence.


## Required branch and review workflow

For every lesson, project or documentation change, create a descriptive feature branch from the latest main, review the change, run relevant checks and open a pull request targeting main. Include actual test results, evidence limits and unfinished assessments. The repository owner reviews and merges. Do not push directly to main, merge automatically, publish packages, create releases or deploy as part of classroom publication.

Every lesson must teach independently: objectives, necessary prerequisites, detailed command explanations, complete code, walkthroughs, tests, knowledge checks with separate answers, assessment criteria, troubleshooting and evidence. Use Sarah for example people and VERIQTA for organizations and systems. Use veriqta for lowercase technical identifiers.
